# Decisions

## 2026-11-25 — One Node script instead of the bash push scripts

Before: The source project pushed cards with `push-card.sh` and dashboards with `push-dashboard.sh` (bash + jq),
and a later project copied the idea into its own `push.sh` with different placeholder rules.
Decision: Ship one tool, `skills/metabase-as-code/scripts/mbac.mjs`, written in Node with no dependencies, that pushes
cards, models, dashboards and collections.
Reason: `mb` itself needs Node 20.6+, so Node is present wherever the skill can work; bash needs jq on top. JSON
handling (placeholder walks, dependency order, diff projection) is clearer in JS than in jq strings, and the tool can
be tested with `node --test` against a fake `mb` (9 tests). shellcheck is not installed here, so a bash version could
not be linted. Two scripts with two placeholder dialects are what made agents reinvent a third.

## 2026-11-25 — Ids per profile in ids/\<profile\>.json, not inside each definition

Before: Each definition json held its production `id`; the local environment kept a separate state file, and the push
script had two code paths.
Decision: Definitions hold no ids. `mbac` writes `ids/<profile>.json` (`collections`, `items[path] = {id,
updated_at}`) for every profile, and resolves placeholders against it.
Reason: The same definitions are pushed to more than one Metabase (local and production in the source project), and
each has its own ids. One mechanism for all profiles removes the special case, and keeps a single place to adopt
existing content by hand.

## 2026-11-25 — Refuse to overwrite items edited in Metabase since the last push

Before: The rule "pull UI edits back before changing anything" lived only in CLAUDE.md; nothing checked it.
Decision: After each push `mbac` records Metabase's `updated_at`. Before an update it compares that with the current
value and refuses on a mismatch unless `--force`; `mbac diff` shows the repo and Metabase side by side.
Reason: The rule was easy to skip. Checked live on Metabase 0.61.3: running a card (`mb card query`) and reading a
dashboard do not change `updated_at`, and an edit through the API does, so the check does not fire on views and does
fire on edits.

## 2026-11-25 — Behavior evals run as separate claude -p processes

Before: skill-creator's default is to spawn a with-skill and a baseline subagent per eval.
Decision: Run each eval as its own `claude -p` process in a fixture project, with the skill copied into the project's
`.claude/skills/` for the with-skill runs, and `mb` restricted to one profile through `XDG_CONFIG_HOME`.
Reason: The subagent attempt was invalid: subagents inherited the parent conversation, and the baseline already knew
about `mbac` and the user's earlier answers. Separate processes start clean, also test that the description triggers
the skill, and cannot reach a production Metabase. Results: `skills/metabase-as-code/evals/RESULTS.md`.

## 2026-11-25 — Placeholder grammar

Before: The source project used `"@database"` and `"@metabase/<path>.json"`; the later project used `"@card:<name>"`,
`"@dashboard:<name>"`, `"@db"`, `"@table:"`, `"@field:"` and `@@...@@` for ids inside strings.
Decision: `"@database"`, `"@card:<path>"`, `"@dashboard:<path>"`, `"@collection:<key>"`, `"@table:[schema.]table"`,
`"@field:[schema.]table.column"`; `@@<same>@@` splices an id into a longer string or a .sql file. Paths are relative
to the content root.
Reason: Paths instead of bare names allow the same file name in `cards/` and `models/`. Table and field lookups by
name were needed when a database was recreated and its field ids changed. The embedded form is needed for links in text
cards and model references in native SQL.

## 2026-11-28 — Create dashboard shells before pushing cards

Before: `mbac push` pushed cards, then created empty dashboards, then filled them, so only dashboards could resolve
`@dashboard:` placeholders.
Decision: Create the empty dashboards first, then push cards, then fill the dashboards.
Reason: The drill-path example needs a card whose SQL returns a dashboard id (`NEXT_DASHBOARD`) for a URL click
behavior; on a fresh instance that card could not be pushed. Creating a shell needs only a name and a collection, so
moving it earlier costs nothing. Test: "a card's SQL can name a dashboard pushed in the same run" (fails on the old
order).

## 2026-11-28 — mbac diff ignores lib/uuid

Before: `mbac diff` compared MBQL `dataset_query` as is; Metabase 0.61.3 adds a `lib/uuid` to every clause it
stores, so every MBQL card showed as changed right after a push.
Decision: Remove `lib/uuid` keys from both sides before comparing.
Reason: Seen on all 8 MBQL cards of the drill-path example. The ids are generated by Metabase and carry no meaning for
the definition. Test: "diff ignores the lib/uuid keys Metabase adds to MBQL clauses".

## 2026-11-28 — Drill-path example: data mapping and "click again to drill"

Before: The prompt asks for industries, customers and shipments, and for "first click highlights, second click on the
same customer drills down".
Decision: On the Sample Database, an order line is a shipment, `PRODUCTS.CATEGORY` is the industry, `PEOPLE.NAME` the
customer. Layer 3 uses quarters, not months. The second click is decided by the data: the ranking SQL returns
`NEXT_DASHBOARD` (layer 3 for an unselected customer, layer 4 for the selected one) and the customer name links to
`/dashboard/{{NEXT_DASHBOARD}}`. Layer 2's shared Y axis is a fixed `graph.y_axis.max` of 1200 on all four cards.
Reason: 1,031 of 1,746 customers bought in all four categories, so "this customer also ships to" has content. Each
customer has only a few orders per category; monthly lines were mostly empty. Metabase click behavior has no state, and
has no axis shared across cards; the busiest industry month is 1,127 units.
